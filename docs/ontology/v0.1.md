# Minimal troubleshooting ontology - v0.1 proposal

Domain definitions and historical examples. The current executable contract is described in [CLAIM-CONTRACT-V02](../CLAIM-CONTRACT-V02.md); these examples still require human validation.

Status: **draft for Gaël's review**, based on pages 97–99 of *Affinity Chromatography Vol. 1: Antibodies*, CY13981-25Jan21-HB. Examples are proposed documentary annotations, not diagnoses or validated instructions for a real process. No example is automatically approved.

Initial scope: HiTrap MabSelect SuRe, increased backpressure, reduced flow and blockage; cleaning and procedural conditions needed to interpret recommendations. The “MabSelect SuRe LX” heading on p.99 starts a different product scope.

## Questions the ontology must answer

1. What phenomenon does the manual describe as potentially increasing backpressure?
2. What action does it recommend when increased backpressure is observed?
3. Does the passage establish the cause in this case, or only describe a possible cause?
4. To which product and process phase does the statement apply?
5. What conditions, quantities and units accompany a procedure?
6. Which exact passage supports the relationship, conditions and parameters?
7. What should the assistant answer if the product, phase or an essential condition is unknown?
8. Can a withdrawn or superseded statement still be presented as active?

## Domain classes

| Class | Definition and example | Exclusions and distinctions |
|---|---|---|
| `Symptom` | Observable undesirable manifestation: increased backpressure, reduced flow, column blockage. | No invented numerical threshold. A symptom in a manual is not an actual observation on the user's equipment. |
| `Cause` | State/phenomenon that may explain a symptom, supported by an explicit relationship. Example: fouling. | Class membership does not establish that the state is present. Cleaning targets may be candidate states without an automatic causal link. |
| `Action` | Documentary intervention/instruction: clean the column, perform CIP, prepare collection tubes. | No guarantee of resolution. Cleaning and CIP remain distinct until equivalence is explicitly justified. |
| `Product` | Named product to which a statement applies: HiTrap MabSelect SuRe. `product_kind` is `prepacked_column` here. | Distinguish prepacked column, medium, instrument, buffer and analytical gel. Do not merge SuRe and SuRe LX. Column volume is a condition, not necessarily a different product concept. |
| `ProcessStep` | Phase/activity contextualizing a statement: elution, CIP, collection preparation. | Water, ethanol and Tris are substances, not steps. A figure title is not a step. |

Buffers/substances in numerical examples remain structured parameter values with evidence. Add `Material` only if questions require retrieving and linking substances; do not extend classes merely to accommodate every sentence.

## Allowed domain relationships

| Predicate | Domain → range | Exact meaning | Prohibited interpretation |
|---|---|---|---|
| `MAY_CAUSE` | Cause → Symptom | The source describes a possible effect under the claim's conditions. | The symptom proves the cause; a quantified probability; a unique cause. |
| `RECOMMENDED_FOR` | Action → Symptom | The source recommends an action when this symptom is observed. | The action always resolves the symptom; the cause is confirmed. |
| `CAN_REMOVE` | Action → Cause | The source says the action can remove the targeted state/substances. | Removal of every cause, guaranteed resolution, equivalence to a symptom-triggered recommendation. |
| `PREVENTS_BUILDUP_OF` | Action → Cause | The source attributes prevention of targeted buildup to the action, with any qualitative frequency. | Remedy for existing buildup or an unspecified numerical frequency. |

`procedure` and `recommendation` also allow a **Claim about an Action**, without inventing a relationship to an absent symptom. Numerical parameters belong to contextualized claims, never to a universal action.

No automatic causality rules in v0.1. Retrieval may follow `MAY_CAUSE` to present a cited possible cause without creating a new assertion or claiming that it occurred. No transitivity: A→B and B→C do not authorize A→C.

## Claims and evidence

Each relationship has a separate `Claim`: `id`, ontology version, type, subject, predicate/object where applicable, source modality, polarity, conditions, parameters and evidence. Different conditions mean different claims even when endpoints match.

| Object | Purpose and minimum fields |
|---|---|
| `Document` | Logical manual identity. |
| `DocumentVersion` | Editorial reference and original PDF SHA-256; distinct conversion identity. A new hash does not overwrite a previous version. |
| `Evidence` | Document version, conversion SHA-256, Docling item, quote reconstructed from raw text, Python character offsets `[start,end)`, original/excerpt PDF pages with explicit bases, coordinates and origin system. |
| `Condition` | Context field, operator, value, role and evidence references. Evaluates true/false/unknown. |
| `Parameter` | Quantity/range, unit, comparator, optional substance/denominator, procedure step and evidence. pH is dimensionless; a column volume is not a fixed mL volume. |
| `ReviewDecision` | Claim/version, human decision, declared reviewer, date and note. `pending`, `approved`, `rejected`, `needs_clarification`. Preserve history; only an explicitly active approved snapshot is served. |

Structural links: `Claim—SUPPORTED_BY→Evidence`, `Evidence—FROM_VERSION→DocumentVersion`, `Claim—APPLIES_TO→Product`, `Claim—IN_STEP→ProcessStep`. Conditions/parameters have their own evidence. These links do not count as extracted causal relationships.

**Content** evidence supports the fact; **scope** evidence supports product/section association. The p.97 heading/introduction supplies product context for subsequent pages. Cross-page scope confirmation remains an explicit review item.

## Conditions and assistant behavior

| Condition | Representation | Example and consequence |
|---|---|---|
| Product | `product_id = product:hitrap-mabselect-sure` | If unknown, ask before presenting a product-specific procedure. If LX, do not extrapolate from SuRe. |
| Severity | `fouling_severity = severe` | Condition for the fouling/effects relationship; a symptom alone does not satisfy it. |
| Trigger | `observed_symptom = symptom:backpressure-increase` | Supports a documentary cleaning recommendation without requiring an intermediate cause. |
| Timing | `timing = directly_after_elution` | Preserves step 9 context for numerical CIP parameters. |
| Undefined necessity | `cip_required = true`, evaluated `unknown` until established | “If required” has no defined criterion; ask or show the condition explicitly, never assume it true. |
| Qualitative frequency | `frequency = regular` | Do not convert into every cycle or a number of days. |
| Sensitive material | `antibody_property = acid_labile_IgG` | Purpose of neutralization on p.98; do not generalize to all proteins. |

Applicability conditions and triggers are conjunctive by default (`all`). Alternatives require explicit `any` and preserved source wording. Missing information is neither a satisfied condition nor a prohibition. `stated_purpose_context` is descriptive: it preserves the source's rationale without filtering applicability. In C08, acid sensitivity explains the note without automatically restricting the general step 1 instruction. The future adapter must preserve this distinction; the local JSON is a draft contract, not a production executable schema.

Distinguish: (1) the source describes a fact; (2) the fact applies to supplied context; (3) the action is authorized in the real process. The prototype prepares the first two; it does not infer the third.

## Constraints and identity

- Application-assigned stable IDs, independent of display names; separate French/English labels and aliases. Readable draft IDs are frozen after review.
- Required domains/ranges, no dangling relationships, no merging solely on similar names.
- Preserve negation, modality (`can`, `should`, `recommend`) and documentary role (`figure_example`, `protocol`, `warning`). Possibility is not certainty.
- Reject numerical procedures when any parameter, unit, denominator or condition lacks evidence.
- Finding a quotation verifies location in the conversion. The PDF, meaning and scope still require reader checks.
- Keep p.97 figure values separate from the p.98 protocol: pH 7.4 and 7.2 must not be merged or automatically treated as a contradiction to resolve.
- The initial catalogue is a small development set written with knowledge of earlier errors, not an independent test or a way to estimate whole-manual recall.

## Difference from the existing schema

`Resin` becomes `Product` with an explicit kind; `Symptom`, `Cause`, `Action` and `ProcessStep` have more precise definitions. Do not mechanically translate `INDICATES`/`RESOLVED_BY`: reread their evidence to choose direction/modality. `APPLIES_TO`/`IN_STEP` belong to contextualized claims. Free-text conditions become structured objects.

This proposal changes neither `ingestion/schema.py`, the database nor existing review decisions. Extractor adaptation follows feedback. Examples therefore do not automatically appear in the review UI on port 8765.

## Reviewing the proposal

Open [the examples](examples-v0.1.md) and the cited PDF pages. Start with C04 (recommendation), C01 (possible cause), then C07/C08 (parameters). Check quotation, meaning, direction, conditions and product scope. An illustrative response in the original review language is: « C04 approuvé pour fidélité documentaire ; C01 à préciser ; C07 à corriger : … ». This is a response example, not a recorded human decision or industrial validation.

Design questions: are the four relationships clear? Is the product correctly modeled as a prepacked column? Do the proposed conditions preserve the text? Are C07/C08 useful to initial scope, or only as numerical-fidelity tests?
